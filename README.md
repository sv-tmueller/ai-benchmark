# AI Benchmark — Prompt Corpus & Artifacts

A curated collection of benchmark prompts and the resulting model outputs.

Two things live here:

- **`prompts/`** — 29 TOML prompt definitions (plus one fixtures file)
  spanning coding, reasoning, math, summarization, creative-writing,
  instruction-following, game-generation, app-generation, domain-probes,
  vision, and ServiceNow-style consulting tasks.
- **`results/`** — collected outputs grouped by prompt family: playable
  HTML game/app artifacts generated by various models, and Markdown
  story/document deliverables.

### Using a prompt with `@prompts/<file>.toml`

Reference any prompt file directly, e.g. `@prompts/game-melon-jelly.toml`;
the `[system]`/`[user]` texts are plain prose and need no preprocessing.
Three caveats:

- **`param-translate`**: its placeholders (`TARGET_LANG`,
  `TEXT_TO_TRANSLATE`) are meant to be replaced with values from
  `param-translate.fixtures.toml` — each `[[cases]]` entry supplies
  `vars.*` pairs (described in the fixtures file as substituting
  `{{variables}}`). Pointing an agent straight at
  `@prompts/param-translate.toml` skips that substitution, so the
  placeholders arrive literally; fill them in yourself or substitute
  concrete values before sending.
- **`vision-shape-count`**: the `[images]` declaration is harness-only;
  when prompting ad hoc, attach `prompts/assets/shapes.png` yourself.
- **Grading**: the `[grading]` blocks in `math-addition`,
  `vision-shape-count` and `sql-country-analytics` are consumed by the
  benchmark harness only; informal runs simply ignore them.

### The `sql-exec` grading mode

`sql-country-analytics` is graded by executing the model's query, not by
matching text. Its `[grading]` block names the fixture DB and the answer key:

```toml
[grading]
mode       = "sql-exec"
fixture    = "harness/fixtures/sql_country_analytics/seed.sql"
answer_key = "harness/fixtures/sql_country_analytics/expected_rows.json"
```

- The mode (`harness/modes/sql_exec.py`) extracts the first ` ```sql `
  fenced block from the Markdown deliverable, builds a throwaway
  `:memory:` SQLite database from `seed.sql`, executes the query once, and
  compares the returned rows to `expected_rows.json` by column name, with
  numerics rounded to 6 decimals.
- A missing result file, a missing SQL block, an empty or no-result-set SQL
  block (e.g. `INSERT`, `CREATE TABLE`, comment-only), a SQL error, a
  malformed or wrong-shaped `answer_key` (anything other than a JSON list of
  objects keyed by column name), a non-string `fixture`/`answer_key` grading
  value, or a row mismatch all yield
  `pass: false` with an explanation in `detail` (and a row diff on
  mismatch) — never a harness crash. The mode returns a verdict for *any*
  input, however malformed; it does not raise.
- The fixture is committed as **text**, not a binary DB, so the database is
  rebuilt per grade call, can never be mutated, and no blob lands in git.
  `harness/fixtures/sql_country_analytics/verify_fixture.py` rebuilds the DB,
  runs a canonical reference query, and asserts the committed answer key
  matches (also covered as a unit test).
- Seed policy: the prompt leaves tie-breaking, NULL handling, and the
  top-product revenue basis to the model, so `seed.sql` is built to make
  every reasonable correct query agree — no NULLs, each `orders.total_amount`
  equals the sum of its line items (so line-item and order-level revenue rank
  the same top product), no product-revenue tie within a country, at least one
  country with `>= 10` orders and one below the threshold, and distinct
  `total_revenue` among qualifying countries.

### Harness: grading results with `grade.py`

`harness/grade.py` grades results retroactively — it never generates new
model output. For every result file whose prompt defines a grading rule it
writes a verdict sidecar `<result>_grading.json` next to the result:

```sh
python harness/grade.py --all              # grade the whole corpus
python harness/grade.py --prompt math-addition   # one prompt only
```

A result is gradable when its prompt TOML carries a `[grading]` block or its
paired `.meta.json` carries a playability verdict. Results with neither are
**skipped, never failed**, as are the harness's own artifacts
(`*.meta.json`, `*_grading.json`, `*_review.html`, `rebuild_verdict*.md`,
images). Prompt association goes through the meta sidecar's `prompt_id`
field, not the filename prefix.

#### `[grading]` spec

Opt-in table in a prompt TOML. `mode` names the module under
`harness/modes/` that grades the result; the module receives
`(result_path, grading, prompt)` and returns a verdict dict. Hyphenated
mode strings map to underscored module files (`sql-exec` →
`harness/modes/sql_exec.py`), while the sidecar `mode` field keeps the
literal TOML string.

```toml
[grading]
mode     = "contains"
expected = "42"
```

- **`contains`** — passes when `expected` appears verbatim in the result
  text; used by `math-addition` and `vision-shape-count`.
- **`playability`** — meta-driven, needs no `[grading]` block; not
  auto-selected by the `mode` field.

#### Playability labels

The `playability` mode reads the browser-verification verdict from
`<stem>.meta.json`, without re-verifying anything. It accepts both shapes
present in `results/`: the newer
`playability_verification.playability_verdict` and the older top-level
`playability.label`.

| Label | Verdict |
|---|---|
| `PLAYABLE_VERIFIED` | pass — the only passing label |
| `BOOTS_ONLY` | fail |
| `BROKEN_AT_BOOT` | fail |
| `BLUEPRINT_ONLY` | fail |
| `BLUEPRINT_INCOMPLETE` | fail |
| `SCRIPT_TRUNCATED` | fail (documented; appears in prose only) |

#### Verdict sidecar schema

`<result>_grading.json`, exactly five keys:

```json
{
  "prompt_id": "math-addition",
  "model": "glm_5_3_flash",
  "mode": "contains",
  "pass": true,
  "detail": "expected \"42\" found"
}
```

`model` is the filename remainder after `<file_prefix>` (from the prompt
TOML, falling back to the prompt id); `detail` is free text explaining the
outcome.

### Execution graders

Three of the prompts are graded by *running* the model's deliverable
rather than pattern-matching its text. Each mode module lives in
`harness/modes/` and exposes `grade(result_path, grading, prompt)`,
returning a verdict dict `{prompt_id, model, mode, pass, detail}` that is
written next to the result as `<result>_grading.json`.

| Mode | Prompt | What it runs |
|------|--------|--------------|
| `python-exec` | `code-flatten-list` | Imports the extracted `flatten` function and drives it through a fixture battery of nested-list cases (including a 5,000-deep case) |
| `script-exec` | `probe-follow-spec` | Runs the extracted Node.js script once per fixture case and compares stdout lines, stderr lines and exit code |
| `sympy-check` | `math-second-derivative` | Parses the boxed `f''(x)` and `f''(2)` answers with `sympy.parse_expr` and checks them symbolically |

Fixtures and expected answers live under `harness/fixtures/<prompt-toml-stem>/`
(`cases.json`, `expected.json`) and never inline in mode code.

**Hygiene.** Model output is untrusted data. Each execution writes the
extracted code into a fresh temporary directory and runs it as a
subprocess with cwd inside that directory, a fixed 10 s timeout and
captured stdout/stderr; timeouts, non-zero exits and exceptions become
`pass: false` verdicts with the captured error in `detail`, never a crash
of the runner. This is *subprocess isolation, not a security sandbox* —
the code is still executed on this machine.

**Runtime.** `python-exec` uses the current interpreter
(`<sys.executable> -I`); `script-exec` needs `node` on `PATH`;
`sympy-check` imports sympy lazily, so `harness/modes/sympy_check.py`
stays importable in stdlib-only environments and its unit tests skip when
sympy is absent. The shared venv (`sympy 1.14.0`) is the reference
interpreter for those tests.

### Harness: scorecard with `scorecard.py`

`harness/scorecard.py` aggregates the committed grading evidence — the
`*_grading.json` verdict sidecars and the legacy `grading` fields in the
`.meta.json` sidecars — into a per-model × per-category pass-rate matrix:

```sh
python harness/scorecard.py    # writes results/scorecard.json + .md
```

The matrix shows a model only when it has at least one verdict; a category
the model has no graded verdict for renders as `—` (an absence, not a
zero), and prompts this harness cannot grade are listed separately, never
counted as failures. There is deliberately no single composite index. The
regenerated `results/scorecard.json` / `results/scorecard.md` are committed
once the grading batch has merged and the full sidecar set exists.

## Flash vs. Frontier: single-shot capability envelope

An ongoing empirical question for this corpus: how much does
single-shot generation quality degrade on flash-tier models compared
with frontier models, and where is the gap widest?

First datapoint — the GLM 5.3 Flash full-corpus sweep (Oct 2026,
batches [#37]/[#97]):

- **Coverage.** 26 of the corpus's 28 prompts ran (29 recorded
  tests); both gradable prompts PASS; probes and text tasks came back
  essentially flawless.
- **Where the cliff sits.** The degradation concentrates in LARGE
  GENERATIVE single-shot artifacts. Of the 7 nominally "playable"
  game artifacts, click-through audits verified exactly 1 (melon-jelly)
  as truly playable: 2 died at boot on shader bugs, 2 scripts were
  syntactically truncated mid-generation, and 2 crashed on entering
  gameplay. On the one apples-to-apples comparison (melon-jelly vs
  Claude Sonnet 5.5 on the same prompt), functionality was at parity
  with a clear aesthetic/polish deficit.
- **Truncation signature.** The two parse-death artifacts
  (cities-skylines, meridian-launch) were exactly the generations that
  raced the 65k reasoning/output budget — burning tens of thousands of
  hidden reasoning tokens before emitting code that cuts off
  mid-expression while the enclosing document still looks healthy.
- **Counterweight.** The best-engineered prompt (horror-house, with an
  explicit shared integration contract) yielded a 13-file project that
  rebuilt with zero defects — flash-tier brittleness scales inversely
  with prompt rigor.
- **Owner-directed takeaway.** Flash-tier variants trade deep
  single-shot reliability for speed/cost: excellent on bounded,
  well-specified tasks, degraded disproportionately on large
  single-shot generative codegen (budget starvation, unproofread long
  code, silent runtime deaths masked by healthy-looking menus/UI
  shells).
- **Practical guidance.** (a) Treat the game/app categories as the
  discriminating tier. (b) Judge playability by click-through +
  sustained animation + per-script parse — never by boot-paint alone.
  (c) Frontier models are expected to clear prompts that flash models
  fail, making those prompts the sharpest comparators.

Planned follow-up: re-running the same game/app tier on a
frontier/non-flash model; results will extend this section with a
direct comparison table.

### Tier-1 comparison: GLM 5.2 vs GLM 5.3 Flash (batch #111)

The 10 discriminating game/app prompts re-run against
`vllm/release/glm-5-2` (non-flash, same family). All numbers below
were recounted from the merged meta sidecars on `main`; the
authoritative narrative is the final comparison comment on #106.

Token economics (9 prompts with flash-era meta; melon-jelly flash
predates the sidecar convention):

| Metric | GLM 5.3 Flash | GLM 5.2 |
|---|---|---|
| reasoning tokens | 221,533 | 228,233 (of which melon-jelly alone: 102,551 ≈ 45%) |
| completion tokens | 564,982 | 404,335 |
| retries | 6 | 5 |

Across the 9 comparable prompts GLM 5.2 burns ~0.57x flash reasoning
and ~0.51x flash completion.

Findings:

- **Zero truncations on both models in this tier.** The flash
  signature weakness (mid-expression cutoff racing the reasoning
  budget) did not manifest here.
- **GLM 5.2 is more reasoning-efficient on well-structured prompts**
  (horror-house: 13x reduction; last-flight: 14x; cities-skylines: 16x).
- **Physics/shader simulations flip the story** (melon-jelly: 102k
  rtok on 5.2; lava-lamp: 5.2 exceeds flash 43k vs 34k).
- **Different retry clustering**: flash retries concentrated on
  large-output prompts, 5.2's on reasoning-heavy physics/shader ones.
- **Comparable structural quality** — all artifacts brace-balanced;
  minor cosmetic flaws on 5.2 (one imbalanced block on
  cities-skylines, an unclosed fence on stillwater, a prose preamble
  on meridian-launch) are not truncations.

Definitive browser-verified playability (supersedes the earlier
boot-paint-era verdicts; see the DEFINITIVE comment on #106):

| Prompt | Flash | GLM 5.2 |
|---|---|---|
| melon-jelly | PLAYABLE_VERIFIED | PLAYABLE_VERIFIED |
| lava-lamp | BOOTS_ONLY | BROKEN_AT_BOOT |
| minecraft | BROKEN_AT_BOOT | BROKEN_AT_BOOT |
| sunset-ocean | PLAYABLE_VERIFIED | BROKEN_AT_BOOT |
| meridian-launch | BROKEN_AT_BOOT | PLAYABLE_VERIFIED |

Both models score 2/5 playable, but on different prompts: flash
handles shader-heavy scenes better (custom GLSL), 5.2 handles complex
multi-system assembly better. Neither dominates; failure modes are
complementary. The five blueprint-tier prompts (horror-house,
mario-kart, last-flight, cities-skylines, stillwater) were assessed
via materialize/build/smoke verdicts rather than the browser harness.

Status note: this covers all 10 prompts; the browser-verifier run
above completes the pending playability verification noted in the
earlier interim comparison.

## Claude Fable 5.2 one-shot arm

A protocol for adding Claude Fable 5.2 to the game/app tier as a plain
one-shot arm, so every run follows the same written rules. Nothing has run
yet; the table below is the ledger.

**Test set (11 prompts).** The 10 game/app-tier prompts of the frontier
sweep above (`game-melon-jelly`, `game-lava-lamp`, `game-minecraft`,
`game-meridian-launch`, `game-sunset-ocean`, `game-horror-house`,
`game-last-flight`, `game-cities-skylines`, `game-mario-kart`,
`app-stillwater`) plus `game-weichensteller`, the only prompt that already
has a Fable 5.1 result
([`weichensteller_claude_fable_5_1.html`](results/weichensteller/weichensteller_claude_fable_5_1.html)).

**Model tag.** `claude_fable_5_2`. Result paths follow the usual
`results/<family>/<prefix>_<model_tag>.<ext>` convention; the family folder
and `<prefix>` come from the existing tree and each prompt's `file_prefix`.
Each deliverable gets a `.meta.json` sidecar next to it.

**Deliverable shape.** Follows the prompt TOML, as in the earlier arms: one
self-contained HTML file for the single-file prompts, one markdown blueprint
for the multi-file project prompts (the same shape as the GLM 5.2 and
gpt-oss-120b arms).

**How to run.** One prompt per run, started with the `/bench-run <prompt-id>`
project skill (added separately), for example `/bench-run game-melon-jelly`.
The prompt TOML under `prompts/` is used unmodified.

**In-session generation caveats.** The generation happens inside a Claude
Code session, not through the gateway runner, so:

- `temperature` and `max_tokens` from the TOML cannot be set; the session
  defaults apply.
- `finish_reason` and token `usage` are not observable. The sidecar records
  them as `null` with a note, exactly like
  [`weichensteller_claude_fable_5_1.meta.json`](results/weichensteller/weichensteller_claude_fable_5_1.meta.json).
- There is no length-retry ladder, so there is no orchestrator or repair
  round: the first complete output is the result.
- Comparisons against the gateway arms (reasoning-token burn, truncation
  events) are therefore qualitative for this arm.

**Verification split.** Generation runs on the small dev box. Browser
verification is a separate step on a stronger machine, because launching
browsers is too memory-heavy for the dev box.

**Verification bar.** The same as the frontier sweep: per artifact, a
click-through transition, sustained animation (pixel motion sampled over
at least 3 s), per-script brace/paren balance, and console capture across
10 s. The result is labelled `PLAYABLE_VERIFIED`, `BOOTS_ONLY` or
`BROKEN_AT_BOOT` (defined in the Playability labels sections above). The
five blueprint rows (horror-house, last-flight, cities-skylines, mario-kart,
stillwater) are not browser-checked as delivered: as in the earlier sweeps,
the blueprint is materialized, built and smoke-tested, and the result may
also be labelled `BLUEPRINT_ONLY` or `BLUEPRINT_INCOMPLETE`. The
[scorecard](#harness-scorecard-with-scorecardpy) only counts a game result
once its sidecar carries `playability_verification.playability_verdict`, so
a result has no playability verdict until this browser check has run;
generation alone does not earn one.

**Merging results.** `python3 harness/merge_results.py --model <model-id>`
(add `--dry-run` to only read and report) squash-merges the open
`<prefix> (<model-id>, one-shot): result` PRs that pass a gate: the prompt
exists and is not parametrized, the branch and folder match, the PR adds
exactly the deliverable and its `.meta.json` (plus `_grading.json` only for
graded prompts) as new files, and the checks are green. A PR that fails the
gate, or that GitHub refuses to merge, stays open with the reason printed;
the command never uses `--admin` or `--auto` and never posts commit statuses.

files are now on `main` to `generated, browser check pending`; that PR is
left for you to merge. Exit codes: 0 done, 1 something stayed open, 2 bad
model id or failed preflight.
